# Refresh token rotation does not invalidate prior tokens (no reuse detection)

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-08-26 07:42:16 UTC
**Target:** http://host.docker.internal:15421
**Endpoint:** /auth/v1/token
**Method:** POST
**CWE:** CWE-613
**CVSS:** 6.5
**Fix Effort:** Low

## Description

The GoTrue token endpoint at /auth/v1/token rotates refresh tokens on use but does not invalidate the superseded token, and there is no reuse detection. A refresh token that has already been rotated can be replayed indefinitely to obtain valid access tokens, so a stolen token cannot be neutralized by rotation and grants a persistent authenticated session.

## Evidence

After password login, the initial refresh token rt0 was rotated into a distinct token rt1 (rt0 != rt1). Replaying the already-rotated rt0 still returned HTTP 200 with a fresh access token each time:
- First replay of old rt0: HTTP 200.
- Second and third replays of the same rt0: HTTP 200 each time.
- The access token minted from the replayed old refresh token was valid against GET /auth/v1/user (HTTP 200, returning the account).
- After a global logout, the same rt0 returned HTTP 400 (refresh_token_not_found), confirming the only effective invalidation is logout, not rotation or reuse detection.

## Impact

Refresh token rotation is intended to cap the damage from a stolen refresh token by making each token single-use. Because previously issued refresh tokens remain valid and are not flagged on reuse, a stolen or leaked refresh token can be replayed any number of times to mint new access tokens, keeping the attacker session alive for the full session lifetime regardless of the legitimate user's token rotation. This weakens session invalidation and extends the window in which a compromised token can be abused.

## Technical Analysis

POST /auth/v1/token?grant_type=refresh_token in GoTrue rotates the refresh token: each successful use returns a new token. The deployment, however, does not invalidate the superseded token or detect its reuse. Replaying an already-rotated refresh token still produces a valid new access token and another refresh token. Rotation therefore provides no real invalidation benefit; the old token's useful lifetime is only bounded by the overall session expiry or an explicit logout. This is consistent with refresh-token rotation enabled but reuse detection disabled, so a stolen token yields a persistent session that legitimate rotation cannot terminate.

## Proof of Concept

1. Log in via POST /auth/v1/token?grant_type=password and record the initial refresh token rt0.
2. Refresh once via POST /auth/v1/token?grant_type=refresh_token with body {"refresh_token":"rt0"}; note a distinct new token rt1 is issued.
3. Replay the original rt0 again; the server returns HTTP 200 with a fresh access token. Repeat to show the old token remains valid.
4. Use the freshly minted access token against GET /auth/v1/user to confirm it is fully functional.

```python
import requests

BASE = "http://host.docker.internal:15421"

def token(grant, body):
    r = requests.post(f"{BASE}/auth/v1/token?grant_type={grant}",
                      headers={"Content-Type":"application/json","apikey":"anon"},
                      json=body, timeout=10)
    return r.status_code, r.json()

_, login = token("password", {"email":"<email>","password":"<password>"})
rt0 = login["refresh_token"]

_, rot = token("refresh_token", {"refresh_token": rt0})
print("rotated?", rt0 != rot["refresh_token"])

for i in range(3):
    code, j = token("refresh_token", {"refresh_token": rt0})
    print(f"replay old rt0 attempt {i+1}: HTTP {code}")

code, j = token("refresh_token", {"refresh_token": rt0})
use = requests.get(f"{BASE}/auth/v1/user",
                   headers={"apikey":"anon","Authorization":f"Bearer {j['access_token']}"},
                   timeout=10)
print("access token from old rt0 works on /auth/v1/user:", use.status_code)
```

## Remediation

Enable refresh-token reuse detection and a reuse grace period in GoTrue (e.g. configure single-use refresh token enforcement and the reuse interval option) so that a previously rotated refresh token is rejected and the affected session is invalidated on reuse. Where possible, revoke all outstanding refresh tokens for a session whenever a new one is issued, and bind refresh tokens to the issuing client to limit replay from a stolen token.

## Assumptions

Exploitation requires the attacker to already possess a valid refresh token (e.g. via an unrelated compromise, a leaked token, or theft). The finding demonstrates that token rotation does not invalidate previously issued refresh tokens, so such a stolen token remains usable for the session lifetime and cannot be neutralized by legitimate rotation.
